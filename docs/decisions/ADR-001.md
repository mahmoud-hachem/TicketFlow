# ADR-001 — Layered Modular Monolith and MongoDB Atlas

**Date:** 19 November 2026  
**Status:** Accepted for the initial TicketFlow MVP  
**Decision authority:** Human project developer; other team members may review and propose revisions.

## Context

TicketFlow is a small object-oriented support-ticket system with six core features and limited academic-project scope. It must demonstrate requirements-driven development, meaningful business rules, tests, and human oversight of AI-generated suggestions. The frontend is React + Vite; the backend is Java 21 + Spring Boot.

## Architecture alternatives

| Option | Benefits | Drawbacks |
| --- | --- | --- |
| Technical-layer monolith | Easy to start | Related feature code may become scattered |
| **Layered modular monolith** | Feature-oriented organization, clear boundaries, testable rules | Boundaries rely on team discipline |
| Microservices | Independent deployment/scaling | Unnecessary networking, deployment and data-consistency complexity for this MVP |

## Architecture decision

Use **one Spring Boot backend** organized by feature (`ticket`, `agent`) with controller/service/domain/repository responsibilities as needed. Keep ticket business rules in directly testable Java code. Use a separate **React + Vite frontend** communicating with the backend through JSON REST APIs.

Proposed structure (will be created during implementation):

```text
TicketFlow/
  backend/
    src/main/java/.../ticketflow/
      ticket/
      agent/
      config/
    src/test/java/.../
  frontend/
    src/
      pages/
      components/
      services/
  docs/
    REQUIREMENTS.md
    decisions/ADR-001.md
  README.md
```

Avoid unnecessary empty layers; keep comments, priorities, assignment and status logic within the ticket feature.

## Database alternatives

- **H2 relational database:** simplest local setup and offline execution, but sharing a development server requires extra setup.
- **MongoDB Atlas:** hosted access from multiple computers, with document persistence; requires internet, controlled network access, credentials, and care to avoid shared test-data conflicts.

## Database decision

Use **MongoDB Atlas** with **Spring Data MongoDB**. The hosted environment supports team development and shared integration testing. Store tickets and agents as separate collections and embed comments in tickets for this small MVP. **Do not use Spring Data JPA**, which was considered when a relational database was proposed earlier.

For dependable collaboration, use separate development databases or clearly isolated test data, with a designated shared integration database. Do not expose connection strings or secrets in GitHub.

## Consequences

- Simple single-backend deployment and clear OOP test boundaries.
- A separate frontend introduces frontend/backend integration work, including CORS and API contract maintenance.
- MongoDB Atlas requires an internet connection, safe credential management and environment setup.
- The MVP has no authentication or enforceable requester/agent permissions; this limitation must remain explicit.
- The architecture may be revised if implementation reveals concrete needs; record such changes in a new ADR or an update with rationale.

## Human–AI decision record

Codex provided an architecture recommendation and identified unresolved scope, workflow and technology decisions. The developer reviewed that advice, chose the layered modular monolith, selected React + Spring Boot, and selected MongoDB Atlas because the project involves a team. The developer also approved the six-feature MVP and its business rules. AI supplied advice; the human made the recorded decisions. No claim is made that tests or application implementation occurred in Phase 1.
